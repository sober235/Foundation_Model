# AUR 128-query 容量修复设计

状态：用户在容量审计及具体128-query方案说明后以“continue”确认接续。按本设计实施、验证并在资源检查通过后启动新版本；不修改旧冻结runtime，不原样恢复run_v3。

## 目标与已完成证据

保持一个模型/一个checkpoint的2D、3D完整A/U/R目标；使真实监督实例能够进入训练，而不跳过高病灶负荷患者、不截断GT、不把超额病灶当背景。原run_v3已完成1725步，下一3D观察65实例超过64query；最近持久化checkpoint1536保留。

容量审计覆盖3499个TRAIN源行、登记Stage II的4096个观察、Stage III对应2048观察子集，以及周期validation的每mode8个固定观察。源体实例最多102；II的2D/3D观察最多14/85，3D有3次超过64；III的3D子集有2次超过64。已有1725条监督匹配计数与独立计数全部一致。完整报告见[容量审计](../../verification/2026-10-26/aur_query_capacity/RESULTS.md)。

## 选项与建议

|方案|收益|代价与限制|建议|
|---|---|---|---|
|固定query从64扩为128|不改变图像、裁块、标签、采样序列和实例定义；覆盖本轮登记观察及当前TRAIN三维源实例上界|新模型配置；query计算量与未匹配query数量增加；需要显式权重来源迁移及资源检查|采用|
|保留64，拆分拥挤裁块|可保持query维度|必须新定义覆盖、边界截断、重复监督权重及步数/患者曝光；改变上下文与训练观察|本轮不采用|
|截取64个GT或跳过超限观察|实现较小|丢弃监督或改变患者分布，不能解决完整目标|拒绝|
|从1536扩query并继续|可能复用已训练A/U头|新增query初始化、Adam状态、学习率位置与旧权重选择需额外迁移；不能称精确恢复|本轮不采用，旧checkpoint仍保留|

建议是新版本固定128个U query，从原通过G1的LR5正式Stage I所选骨干重新开始Stage II。不是把旧run_v3改成成功，不将新运行记作step1536或1725恢复。先前消耗的训练另行记录。

## 改变与保持

唯一模型结构变化是U query槽位64→128。默认旧64配置和旧证书继续可读，只有显式新登记选择128。A32、R13+no-host、骨干、query维度、A/U/R损失公式与权重、采点策略、病例/序列抽样、crop尺寸和增强均保持。未匹配query增多会改变原加权存在性loss的构成，这是容量变化的实际影响；本轮不另外补偿权重或声称训练轨迹等价。

数据资格合同和医学文件不改；仍使用原3499 TRAIN/405 development validation。实际训练每阶段仍完整验证源字节。新运行树从原冻结runtime复制后只覆盖经审阅的必要代码，拥有新摘要；原runtime与全部旧登记/权重/诊断保持字节不变。

128对当前TRAIN三维source-instance上界102具有覆盖保证，前提是原资格和保持源ID的3D裁块规则不变。2D可能把一个3D实例分裂为多个平面组件，当前最大14只适用于已审计的登记观察，不是所有未来二维裁块的全局上界。新数据、seed、采样/增强或预算变化必须重新审计，不得沿用这份结论。

## 容量接口

1. 模型配置显式登记`n_events=128`；支持范围和类型由统一配置检查控制，保留64默认值。
2. `make_unified_crop`按登记容量检查，不再硬编码最多64；超过实际登记容量仍拒绝，不能截断。3D与2D都保留原实例、面积/体积门槛和监督资格。
3. 二维弱关系接口新增显式容量参数，由crop的`n_events`传入`_qualify_geometry`；默认64向后兼容。不能仅扩大U decoder却让R仍在64处拒绝。
4. `_batch`继续检查实例数不超过模型容量；推理/评价中报告的容量从模型配置读取。旧固定64饱和计数若继续使用必须明确标为旧指标，不能混作128模型容量。

## Stage I 到新Stage II：显式来源转换

现有Stage II准入要求父子model_config和runtime identity完全相同。不能改写旧Stage I导出、证书或G1报告的字段来通过它。

新增仅供本次容量变化的显式初始化策略（实现名称由计划确定），在新登记中绑定：原父export/completion/G1哈希、原runtime摘要、新runtime摘要、新完整recipe摘要、数据合同和geometry版本，以及唯一允许的模型差异`n_events:64→128`。

- 使用父证书原本的data/runtime身份验证原Stage I完成证书及双mode G1，保持原对象原字节，不给旧证书换身份。
- 子模型具有自己的新runtime身份；要求数据合同SHA和geometry版本与父一致，全部骨干配置一致，其他模型字段除`n_events`外一致。
- 核验骨干相关实现的依赖闭包未变，并对比加载后的全部骨干张量与原export完全一致。保留原G1为父骨干证据，不伪造新运行G1成绩，不重复已完成G1拟合。
- 新A/U/S/R任务头按登记seed初始化；不载入旧run_v3的监督权重、optimizer或RNG。Stage II步数从0开始，optimizer/scheduler新建。
- 子运行的lineage、run_config及完成边界保存转换策略与双方源承诺。未知策略、不同数据/几何、非Stage I父、修改骨干或其他模型差异均拒绝。
- 默认同身份初始化与已有strict resume规则保持；普通旧配置不能借此绕过验证。
- **正式III**只接收本次新runtime、新128模型的完整正式II证书；正式II失败就不启动正式III。

这属于可审计的权重迁移，不是精确checkpoint恢复，也不承诺未来CUDA更新逐位一致。

## 预算、检查与启动顺序

正式预算建议仍为II4096、III2048，2D/3D交替，batch1/accumulation1，seed20261019，2D1×160×160、3D128×160×160，16384点。学习率沿用II backbone5e-5/heads5e-4、III backbone1e-5/heads2.5e-4/relation5e-4；warmup128/64，保存256、验证512，两mode各8批并等权loss选点。

正式时间上限暂沿用II14400秒、III7200秒、整个控制器28800秒；是否满足128模型性能必须由有限probe证实。若资源probe预测不满足，先提交明确预算修订，不能悄悄延长。训练工程可运行不代替最终A/U/R评价。

执行顺序：

1. 代码与回归：65/85/102/128实例能完整构造目标与匹配；129仍拒绝。二维分裂组件和R容量同步，默认64仍拒绝65。测试父证书完整性、唯一允许配置差异、不同runtime显式绑定、迁移后骨干等值、旧strict恢复拒绝不匹配。
2. 合成端到端：小模型完成双mode II→III、所有目标参与匹配、非活动适配器不更新、完整保存恢复；没有真实权重冒充synthetic purpose。
3. 冻结新运行树与完整登记，独立代码/精确登记复核，全套CPU检查及适用CUDA检查。私有日志只发布匿名计数/哈希。
4. 有限真实resource_probe：事先冻结8步II和8步III、两mode各4次曝光；3D包含65和85实例压力观察，2D与3D各至少有合格R监督观察；压力观察本身可以没有R资格，但所有U实例都必须匹配。8步是独立执行上限，scheduler仍使用正式4096/2048步和warmup128/64。probe II从原正式Stage I按显式迁移策略初始化；**probe III**只接收本次完成8步的probe II导出，并核验purpose、阶段、步记录/哈希以及相同新runtime/模型/数据身份，不伪造正式II证书或用synthetic权重。记录有限loss、容量匹配、R参与、每步LR/时长/显存及独立验证/保存耗时；8个特选观察不能可靠外推全预算耗时。预算不足则先修订登记。
5. 通过后，从同一原正式Stage I骨干重新启动新正式II，不继承probe更新。按宿主机可见性、调度约束、实时负载选择兼容空闲GPU，保存所有准入和拒绝测量，后台有限watchdog。
6. 完成后按原验收规格先在development validation选工作点/关系实现，再冻结历史test最终判门和全量fastMRI配置。64-query旧结果作为历史，不与128模型的质量混写；容量解决并不保证最终质量。

## 回退与本次待确认决定

所有改动在唯一登记工作分支推进，旧runtime、run_v2/run_v3及1536 checkpoint不改。新运行只写新私有目录；失败停止保留证据，不自动无限追加训练。回退可回到旧代码和权重做只读回放，但旧64运行不能绕过已知失败继续。

本次需要确认的实际取舍：采用128-query新模型，并从原LR5正式Stage I重新执行II4096→III2048，而非迁移1536监督checkpoint或拆分裁块。代价是重做正式监督预算和一次有限资源probe；收益是保持原观察/标签与损失定义，避免额外optimizer和目标覆盖迁移。
