# 下一项实验契约草案：冻结模型，保留 U query 的实例信息

状态：六例诊断后的研究建议；尚未实现、未运行、未被当作生产修复。模型目标仍是 A32 / 统一异常实例 U / 每实例 R13 + no-host。

## 假设与唯一主变量

假设：当前先把不同 query 概率取 max 再提连通块，会把原本能定位的病灶组件连接到背景/其他异常，从而损害实例检测。六例中有同窗直接证据，但高质量 query-CC 是 GT 事后 oracle，尚不知无需 GT 的候选选择能否达到可接受误报。

保持 checkpoint、A/U/R 所有参数、输入、presence >0.5、mask ≥0.3、BMSR/ISLES/PDGM score 0.70/0.60/0.75、valid、26CC 及 10 mm³ 规则；**只研究实例解码的表示方式**，不用训练、病种头、阈值搜索或 N7 语义头替代它。

## 先写清楚再实现的解码合同

1. 原路径保留为 `legacy_max`。候选路径从每个自然窗口的已保留 query 分别取连通组件，带上 `(window_start, query_index, component_index)` 和有效体素坐标；GT 不参与选 query、选组件、去重或评分。
2. 每个候选的 score 来自它自己的原始 float32 概率；不能用 GT IoU 排名，也不能拿 float16 代表缓存冒充所有组件的原分数。
3. **跨窗去重、重叠体素归属和 R token 归属须在实现前写定并测试。** 不同窗口同号 query 不等于同一异常；不能直接把组件全收下，也不能把它们重新无条件 union 成原来的大块。第一版应采用一个明确、确定性的候选排序与重复抑制规则，并锁定其参数，分别报告重复候选和被抑制候选。
4. 保持 A 输出完全不变。R 受控轨道先沿原调用路径对照，避免把 U 解码和 R 几何修复混在一起；端到端 R 对新增 U 实例的裁块/token 来源必须明确记录，输出仍为每实例 14 类概率。该接口未完成就只能叫 U 解码诊断，不能叫 A/U/R 交付。

上述第 3 项是实施设计必须解决的内容，不能由执行者在看到验证结果后随意选规则。当前缓存分析不具备所有组件的精确 float32 分数，不能声称已完成这个 GT-free 对照。

## 运行与判据

- 先用同一冻结六例检查候选路径与原模型 A 的一致性、实例/来源追踪，以及完整误报数量。六例用于通路核验，不选超参数、不判正式门。
- 然后固定代码、规则与参数，在完整 frozen val 上比较 U 各源的灵敏度–误报工作点，沿用 S7 参考预算与匹配规则，报告各来源和大小分层。不能只报 GT-best 组件覆盖或只报召回。
- 同时报告 A32/13 宿主和 R controlled、端到端覆盖及 rescue/harm。检测集合改变时，端到端 R 子集不能直接当作配对的总体关系提升。
- 若同误报预算下 U 没有收益，记录失败；回到固定 train 裁块的监督、匹配和 dense mask 拟合检查。不要继续叠加训练/阈值修改。若有收益，冻结后续完整模型验收契约，再安排最终测试。
- A 五个实体缺失需单独检查监督点正样本覆盖与 mask 身份竞争；R coarse/dense 失配需单独进行固定 token、逐项替换几何来源的诊断。两项均保留，不以 U 进展销账。
